# Phase quick-260816-7c0 Plan 01: Give python-ai Template Docker Access Summary

Docker CLI + Compose plugin added to the python-ai workspace image via docker-outside-of-docker (host socket mount + group_add), giving developers `docker` and `docker compose` without a nested engine.

## What Was Built

### Task 1 — Dockerfile: Docker CLI + Compose plugin install block

Added a new build block to `templates/python-ai/Dockerfile`, placed after the PostgreSQL + pgvector block (which ends at the `initdb --version` line) and before the final `USER coder` line.

The block:
- Fetches Docker's official GPG key from `https://download.docker.com/linux/ubuntu/gpg` into `/etc/apt/keyrings/docker.gpg` (`chmod go+r`)
- Writes an arch-aware apt source to `/etc/apt/sources.list.d/docker.list` using `$(dpkg --print-architecture)` and `$(. /etc/os-release && echo "$VERSION_CODENAME")`
- Installs **only** `docker-ce-cli` and `docker-compose-plugin` — no engine, no containerd, no buildx (DooD, not DinD)
- Ends with `apt-get clean && rm -rf /var/lib/apt/lists/*`
- Block comment explains: DooD mechanics (host daemon, sibling containers), and two operator gotchas: (a) compose bind-mount paths resolve against HOST fs; (b) socket access = effective host root

The existing PostgreSQL block note ("Docker-in-Docker is structurally unusable inside this workspace container") is untouched and remains accurate — it concerns a nested engine (DinD), which is a completely different mechanism.

## LIVE-VERIFY Deploy Gate (Outstanding — Required Before Trusting in Production)

Static checks (`terraform fmt -check`, `terraform validate`) are necessary but NOT sufficient (per project memory "infra-needs-live-deploy-gate"). The following live deploy steps MUST be completed before this change is relied on:

### Steps

1. **Push the template to the Coder server:**
   ```bash
   cd templates/python-ai
   coder templates push python-ai --yes
   ```

2. **Create (or rebuild) a workspace** from the `python-ai` template in the Coder UI.

3. **Inside the workspace, verify Docker works:**
   ```bash
   docker ps                     # must list host containers (host daemon)
   docker compose version        # must report the compose plugin version
   # Smoke test — start a sibling container:
   docker compose -f - up -d <<'EOF'
   services:
     hello:
       image: hello-world
   EOF
   docker compose -f - ps
   docker compose -f - down
   ```
   Expected: `docker ps` lists host containers (not an error), compose starts a sibling container on the host.

4. **Confirm host socket GID matches the default:**
   ```bash
   # On the HOST (not inside the workspace):
   stat -c '%g' /var/run/docker.sock
   ```
   Expected: `999` (Debian/Ubuntu Docker Engine standard). If the output differs from `999`, the operator MUST override `docker_group_id` to the actual GID in the workspace template parameter, otherwise `docker` inside the workspace will return "permission denied".

5. **Confirm no false "docker ps" from a pre-existing container:** the output of `docker ps` inside the workspace should include the workspace container itself and other host containers — confirming it talks to the host daemon, not an empty local one.

### Operator Gotchas to Verify in Practice

- **Compose bind-mount paths resolve against the HOST filesystem.** A volume like `./data:/app/data` in a workspace compose file mounts `./data` relative to the HOST's current directory, not the workspace's. Test this explicitly if your developers use compose bind mounts.
- **Socket access = effective root on the host.** Any process in the workspace can start privileged containers, read host files via volume mounts, or escape the workspace. This is acceptable for a single-operator self-hosted Coder setup (the intended use case), but is NOT appropriate for a shared or multi-tenant deployment.

### Claude Code dev container nesting caveat

The Claude Code dev container (if launched from within a python-ai workspace) runs one level deeper inside the workspace container. The socket mounted into the workspace container (`/var/run/docker.sock`) IS visible inside the Claude Code dev container because it lives on the same filesystem namespace — but only if the dev container is started with access to the workspace's `/var/run/docker.sock`. If `docker` commands inside Claude Code's dev container return "permission denied" or "cannot connect to the Docker daemon", the dev container itself may need the socket passed through (e.g., via a docker-compose override that mounts `/var/run/docker.sock` into the dev container). This is an operator configuration detail, not a template defect.
