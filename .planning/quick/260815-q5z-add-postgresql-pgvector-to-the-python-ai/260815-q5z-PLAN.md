<objective>
Give the `python-ai` Coder workspace template a first-class, persistent PostgreSQL 18 +
pgvector database.

Purpose: AI/RAG work in this template needs a local vector store. Docker-in-Docker is
structurally unusable inside the workspace container (user-probed: `iptables -t nat -N DOCKER`
-> Permission denied, `unshare: operation not permitted` — no NET_ADMIN, no namespace
creation), so Postgres cannot run as a nested container. It must be baked into the workspace
image and started by the agent.

Output: an image layer that installs `postgresql`, `postgresql-contrib` and
`postgresql-<major>-pgvector`, plus an idempotent `startup_script` block that runs the server
as the `coder` user with `PGDATA` on the persistent `/home/coder` volume, creates a generic
`coder` database, and enables the `vector` extension.
</objective>

<design_constraints>
1. PERSISTENCE: the `docker_container` is ephemeral (recreated on every stop/start). Only
   `/home/coder` (docker_volume.home_volume) and `/home/coder/.claude-shared` persist. The
   Debian auto-created cluster at `/var/lib/postgresql/18/main` lives in the container layer
   and would be WIPED on every restart — that is why this plan runs `initdb` as the `coder`
   user with `PGDATA=/home/coder/.pgdata` instead of using `pg_ctlcluster`.
2. TERRAFORM HEREDOC ESCAPING: `startup_script` is a `<<-EOT` heredoc with Terraform
   interpolation active. Shell `${VAR}` brace syntax would be eaten by Terraform. Use bare
   `$VAR` forms only (the existing script already does: `$HOME`, `$CLAUDE_SHARED`). If a brace
   form is ever unavoidable, escape it as `$${VAR}` (see the `coder stat disk --path $${HOME}`
   metadata block).
3. WARN-AND-CONTINUE (WR-03): `startup_script` begins with `set -e`. Every new command must be
   guarded with `|| echo "WARN: ...; continuing" >&2` so a Postgres problem never aborts the
   Claude/MCP/GSD/clone plumbing that follows.
4. VERSION-AGNOSTIC: do not hardcode `18` in shell paths. Derive the major from
   `/usr/lib/postgresql/*` so a base-image bump to Postgres 19 does not silently break the
   template.
5. SCOPE: touch ONLY `templates/python-ai/`. Do not modify other templates, `compose.yaml`,
   or `scripts/`.
6. IMAGE REBUILD: `docker_image.main.triggers.dockerfile_sha1 = filesha1(Dockerfile)` — editing
   the Dockerfile automatically invalidates the cached image, so the new layer is picked up on
   the next workspace start/update with no extra wiring. Nothing to change there.
</design_constraints>

Add ONE new `RUN` block to `templates/python-ai/Dockerfile`, inserted after the GitHub CLI

a `# ── PostgreSQL + pgvector ──…` banner comment explaining WHY (DinD unusable in the
workspace container per the live probe; PGDATA lives on the persistent home volume, not in the
Debian cluster), then a single `RUN set -eux; \` chain.

The RUN chain must, in order:
1. `apt-get update` and `apt-get install -y --no-install-recommends postgresql postgresql-contrib`.
2. Derive the installed major version dynamically — `PG_MAJOR="$(ls /usr/lib/postgresql | sort -V | tail -1)"` — then `apt-get install -y --no-install-recommends "postgresql-$PG_MAJOR-pgvector"` (constraint 4: never hardcode `18`).
3. Drop the Debian auto-created default cluster, which is dead weight in the container layer and
   would confuse operators into thinking it is the live database:
   `pg_dropcluster --stop "$PG_MAJOR" main 2>/dev/null || true` (guarded — the postinst may not
   have created one under a container build).
4. Make the unix socket directory writable by the workspace user. This is REQUIRED: Debian builds
   compile the default `unix_socket_directories` to `/var/run/postgresql`, which the package
   creates owned by `postgres:postgres`; the `coder` user could not create its socket there and
   the server would refuse to start. Use `install -d -o coder -g coder -m 0775 /var/run/postgresql`.
5. Write `/etc/profile.d/20-postgres.sh` (mirroring the `10-uv.sh` precedent) exporting
   `PGDATA=/home/coder/.pgdata`, `DATABASE_URL=postgresql://coder@localhost:5432/coder`, and
   prepending the versioned bindir to PATH. IMPORTANT quoting: build the PATH line with
   `printf 'export PATH="/usr/lib/postgresql/%s/bin:$PATH"\n' "$PG_MAJOR"` — the single-quoted
   format string keeps `$PATH` literal in the emitted file while `%s` expands PG_MAJOR at build
   time. Then `chmod 0644 /etc/profile.d/20-postgres.sh`.
6. `apt-get clean` and `rm -rf /var/lib/apt/lists/*` (house convention).
7. Self-assert inside the layer: `"/usr/lib/postgresql/$PG_MAJOR/bin/initdb" --version`.

Do not add an `EXPOSE`, do not publish a port, and do not change `USER coder` placement.

Before/alongside the edit, PROVE the runtime design offline (this de-risks Task 2): write a
two-part smoke script into the scratchpad dir and run it inside a throwaway container off the
same base image (`codercom/enterprise-base:ubuntu`, run with `--user root` since the image's
default user is `coder`). Root part: the apt install + PG_MAJOR derivation + socket-dir
`install -d` above. User part (executed via `su -l coder -c 'bash /smoke-user.sh'`): run

  project-specific database name.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workspace container -> host | Postgres listens on the container's loopback only; `docker_container.workspace` publishes no ports, so nothing is exposed to the host or LAN |
| workspace user -> database | The `coder` OS user is the DB superuser by construction (initdb -U coder); single-tenant workspace, no privilege boundary intended |
| Ubuntu apt repos -> image | New build-time packages fetched over apt |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-q5z-01 | Information disclosure | Postgres listener | accept | initdb default `listen_addresses = 'localhost'` + no published port + no `host` entries in pg_hba beyond loopback. Single-tenant workspace container owned by one Coder user. Plan explicitly forbids widening listen_addresses or adding a port mapping. |
| T-q5z-02 | Elevation of privilege | `sudo install -d /var/run/postgresql` in startup_script | mitigate | Fixed, non-interpolated argument list; no user-controlled input reaches the sudo call; failure is warn-and-continue, never a retry loop. Primary path is the Dockerfile chown — the sudo is only a tmpfs `/run` safety net. |
| T-q5z-03 | Tampering | apt packages (`postgresql`, `postgresql-contrib`, `postgresql-<major>-pgvector`) | accept | Ubuntu default archive, signed by the distro keyring already trusted by the base image. No third-party PPA is added. Package Legitimacy Gate (npm/pip/cargo) is N/A — no language-ecosystem installs in this change. |
| T-q5z-04 | Denial of service | startup_script | mitigate | Whole Postgres block is guarded and warn-and-continue under `set -e`; a failed initdb/start cannot abort Claude/MCP/GSD/clone setup that runs before it, and it cannot loop. |
| T-q5z-05 | Information disclosure | `DATABASE_URL` in agent env | accept | Contains no password (trust/peer auth on a loopback-only, single-tenant server); it is a convenience DSN, not a secret. |
</threat_model>
